# Architecture

Python 3.11+ orchestrates. The heavy work is native: `zsign` signs the IPA, and a current `ideviceinstaller` / `usbmuxd` / `libimobiledevice` built from pinned git commits talk to the phone. Bookworm's packages (libimobiledevice 1.3.0, ideviceinstaller 1.1.1) do not. A Zero W has 512 MB and an ARMv6 core. That rules out the tools people usually reach for, which is why they are not vendored here.

## What was not used, and why

- **NyaMisty AltServer-Linux 0.0.5.** The published binaries are armv7, aarch64, i586, and x86_64. An armv7 binary does not run on a Zero (it dies with SIGILL). Its bundled `ldid` signer writes a code directory with both SHA-1 and SHA-256. AMFI on iOS 17 and later rejects that (the report is code 85). This project signs with `zsign -2` so only SHA-256 is requested. That flag is the published fix; it was not re-checked on a device in this repo.
- **dragoshont/AltServer-Linux.** It does switch the signer to zsign and has been reported working on new iOS, but the build wants Boost, cpprestsdk, and corecrypto, and the containers are amd64/arm64. That is not a fit for this board.
- **Dadoum Sideloader and splice.** Written in D. There is no reliable ARMv6 toolchain story, and the anisette side loads Apple's ADI shared library (armeabi-v7a / arm64 / x86 only).
- **sideloop, and AltServer in Docker.** amd64/arm64 images. A Zero cannot run them.
- **netmuxd.** A Rust proxy for AltStore's heartbeat protocol. There is no ARMv6 build, and this project installs with `ideviceinstaller` directly, so it does not need that heartbeat.
- **A local anisette provider.** Same ADI library problem. The Pi calls a remote anisette-v3-server. `GET /v3/client_info` is the User-Agent and `X-MMe-Client-Info` pair (AltSign pull 61, required since 12 October 2026). `GET /` is only the one-time password; its client-info string is not the one Apple checks. The server's identity has to persist on disk or Apple asks for a code on every login. There is no default public server. `hsc` 434 retries the login once only after `POST /v3/resync` or `GET /reprovision` returns success. The current v3 server implements neither, and restarting it does not apply a resync. Login stops. Wipe that server's provisioning data and let it provision again, or wait and retry.

`zsign` is C++ and MIT-licensed. The install script checks out the commit that merged pull 391 (SHA-256-only by default, canonical DER entitlements) and builds with `make -C build/linux -j1`. A binary already on the Pi is replaced unless its stamp file is that commit. The same pins and build function live in `scripts/phone-stack.sh`, which is what both the Pi source build and the prebuilt workflow call. The workflow targets ARMv6 on purpose (`-march=armv6` inside a Raspbian Bookworm armhf rootfs). Debian's armhf port is ARMv7 and will not run on a Zero. When `prebuilt/armv6.env` names a `prebuilt-*` release whose sha256 matches, an armv6l install checks every tarball member, copies only `usr/local/{bin,sbin,lib,share/sideload-pi}`, runs the tools, and only then writes the stamp files. A bad member, a bad checksum, a failed tool check, a missing release, an offline Pi, or any machine that is not `armv6l` compiles instead. A failed tool check removes what that attempt copied and leaves no stamp files. A tarball rejected before the copy leaves an existing install alone. `--build-from-source` skips the download and rebuilds even when the stamps already match. A `prebuilt-*` tag publishes the artifact from that commit's earlier successful build. It does not compile again. The workflow rejects the tarball unless every executable and shared library has `Tag_CPU_arch: v6` exactly (`v6KZ` and `v7` do not pass) and `qemu-arm -cpu arm1176` can run `zsign -v` and `ideviceinstaller --help`. Raspbian Bookworm's own gcc and C runtime are already tagged v6. Object files compiled as v6KZ or v7 fail the job. A linked file that is only v6KZ because something in the runtime was, and whose own objects were v6, is retagged to v6. A v7 tag is left as it is and fails the job. The key and certificate are PEM files mode 0600. The password is not passed on the command line, because `ps` would show it. `-E` and `-W` strip extensions and a watch app by default so they do not consume App IDs. `-f` replaces a profile that changes every week. FairPlay payloads (`SC_Info/`) are rejected before signing.

## Apple, at the level the code follows

The login and provisioning calls follow AltSign (pull 61's `ALTAppleAPI+Authentication.swift` for the post-October 2026 identity, and the older authentication code for SRP) and the pure-Python client in nythepegasus/grandslam. They were not executed against Apple's servers in CI. Password, SPD, negotiation, and app-token tests compare frozen known-answer bytes. A local SRP peer still checks the handshake glue. Neither proves that Apple still speaks this dialect.

- GrandSlam `POST https://gsa.apple.com/grandslam/GsService2`, plist, header version 1.0.1.
- SRP through the `srp` package's pure-Python module with `rfc5054_enable()` and `no_username_in_x()`. That is the combination those clients use to avoid error `-22406`. The password material is PBKDF2-HMAC-SHA256: `s2k` uses the raw SHA-256 of the password, `s2k_fo` uses the hex of that digest.
- SPD is AES-256-CBC. The key is HMAC-SHA256 of the session under `"extra data key:"`, and the IV is the first 16 bytes of the same under `"extra data iv:"`.
- The negotiation proof is checked. A missing or mismatched proof is a hard failure. The length prefix in that digest is little-endian. This was not confirmed live against Apple.
- `pysrp`'s `User.verify_session` returns `None` even when the proof matches, so the code checks `authenticated()` afterwards.
- A trusted-device code is `GET /auth/verify/trusteddevice` and then `GET /grandslam/GsService2/validate` with a `security-code` header. `hsc` 409 with an empty `au` means Apple already sent that code, so the client does not request another one. SMS reads `trustedPhoneNumbers` from `GET https://gsa.apple.com/auth` and sends the id the owner picks. After a code is accepted the whole login runs once more. A second code request fails closed.
- The GSA `cpd` dictionary is the string-only shape from AltSign pull 61 (`bootstrap` `"true"`, not a boolean). User-Agent and `X-MMe-Client-Info` are the anisette pair. `X-Xcode-Version` on those requests is `27.0 (27A5218g)`, the value that pull sent. Redirects are not followed.
- The Xcode token is not `GsIdmsToken`. An `apptokens` request for `com.apple.gs.xcode.auth` returns `et`, unwrapped as AES-GCM with the `XYZ` envelope those clients document. `X-Apple-GS-Token` is base64 of `adsid + ":" + that token`.
- Developer services are `https://developerservices2.apple.com/services/QH65B2/` with client id `XABBG36SBA`. The calls used are list teams, list/add devices, list/add App IDs, submit a development CSR, and download the team profile. Result `9120` is the App ID limit. HTTP 401 logs in once and retries once.
- The profile expiry is read back out of the CMS profile (the embedded XML plist), not assumed to be 7 days. A profile whose lifetime is 8 days or less, or whose `IsFreeProvisioningProfile` is true, marks the account as free.
- A fourth device is blocked locally only after the account is already known to be free. Otherwise the add is attempted and Apple's error is shown. There is no reliable "free team" flag on `listTeams` (a free personal team and a paid individual team can both come back as Individual).

The development key is RSA 2048, stored unencrypted at mode 0600 so zsign does not need a passphrase. The certificate is reused until it expires inside the refresh margin. Replacing it revokes only the certificate this tool recorded (serial and id in `secrets/development.json`), using the v1 certificates API SideSign uses for a free team (`POST` with `X-HTTP-Method-Override`). If Apple then says the slot is full (result 35 or 7460), that same certificate is revoked and the CSR is submitted once more. Other certificates on the account are left alone. An App ID that has disappeared from `listAppIds`, or a profile download of 8201, 9100, or 9115, is created again and counts toward the 10-per-7-days window.

## The daemon

`tick(now)` is one pass and is what the tests call. The process handles `SIGUSR1` (udev, or `sideload-pi refresh`) and `SIGTERM`. One due app per pass. A force file ignores the due date and the backoff. State lives in `/var/lib/sideload-pi/state.json` and does not contain the password. The daemon reloads that file at the start of each tick, and every save takes an exclusive flock on `runtime/daemon.lock`, so a CLI add is not overwritten by the in-memory copy. A corrupt `state.json` is moved to `state.json.broken-<time>` and the loop continues with an empty library. Live phase is `runtime/status.json` (pid included). `sideload-pi status` reads that file when the pid is alive; a fresh process would otherwise always report idle. The unit is ordered `After=` and `Wants=` `time-sync.target` only. It is not ordered on `systemd-time-wait-sync.service`, and install does not enable that oneshot: `sideload-pi enable` runs `systemctl enable --now`, which would hang until NTP. The daemon process starts and paints `waiting_for_clock`. A tick does not refresh unless the clock is at least 2026-01-01 and `ntp_synchronized()` is true. That helper returns None only when the `timedatectl` binary is absent, and then only the date check applies. A non-zero exit, a timeout, or stdout other than `yes` returns False and the tick waits. Logs go through a filter that strips password, token, and anisette header values.

USB is preferred. `idevice_id -l -n` and `ideviceinstaller -n` are the Wi-Fi path, after a USB pair. If `ideviceinstaller list` already shows the bundle, the install is an `upgrade` so the app's data stays. Progress lines are the ones `ideviceinstaller`'s status callback prints: `Install: Stage (N%)`, with a carriage return between updates. When the tool omits a percent, a fixed stage table moves the bar. A percent from the device always wins.

## The panel

UI bitmaps are 250×122, mode `1`, drawn with Pillow's default font. The driver rotates them into the controller's 122×250 buffer. V2 and V3 use the lookup tables from Waveshare's demos. V4 uses that demo's fast-refresh commands (it does not take a software LUT the way V3 does). V3 and V4 partial updates pulse RST low for 1 ms, which is `displayPartial` in those demos, not the 20/2/20 ms full reset. V1 follows `epd2in13.py`: different init (booster, VCOM, a 30-byte LUT), a different bitmap pack (no V2 mirror), and a full-frame update command `0xC4` written a row at a time. See [SETUP.md](SETUP.md) for the sticker and the `display-test` command. `display-test` refuses to run while `sideload-pi.service` is active.

Busy is high while the controller works. That matches all four demos.

## The battery

CW2015 at I2C `0x62` on bus 1, the way the UPS-Lite v1.3 vendor script reads it. `smbus` word reads are byte-swapped. Voltage is `raw * 0.305 mV`. State of charge is `raw / 256` (the high byte is the integer percent). A quick-start writes word `0x30` to register `0x0A`. GPIO 4 is high when the adapter is in, and only if the pads are soldered. Shutdown requires that signal to be explicitly enabled and to read "not charging", twice, under the threshold. An I2C error never shuts the Pi down.

## USB power

Documented in [SETUP.md](SETUP.md). The data-port VBUS pin is wired to 5 V. The service does not try to clear a sysfs bit that this board does not have. The practical mitigations are a powered hub, a data-only cable, and leaving the UPS charger connected during a refresh.

## The web page

A threaded stdlib HTTP server inside the daemon, bound to loopback unless `web.allow_remote` is set. Token in an HttpOnly cookie or a Bearer header, compared in constant time. An IPA upload is streamed to disk in chunks. The default cap is 64 MB (`web.max_upload_mb`). No token in the query string. The service user is `sideload`; root is still required to install packages, install udev rules, and enable the unit.
